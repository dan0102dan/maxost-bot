# Эксплуатация

## Проверка перед открытой регистрацией

Начните с `ALLOWED_TELEGRAM_IDS` для двух тестовых пользователей. Проверьте вход,
личный диалог, группу, канал с/без прав записи, фотоальбом, подпись и замену медиа,
опрос (включая множественный выбор), `/react` и неизвестное вложение.
Отзовите сессию в MAX: бот должен остановить её и уведомить о повторном входе,
не посылая SMS. Перезапустите контейнер и повторите тест с очередью.
Реальные аккаунты и их токены не используются в CI.

## Автотесты

```bash
python -m pip install . -r requirements-dev.txt
ruff check maxost tests
pytest -q
```

Без `TEST_DATABASE_URL` PostgreSQL-тесты пропускаются; используйте только
**одноразовую тестовую БД**: тесты очищают её таблицы. GitHub Actions поднимает
PostgreSQL 17, выполняет все тесты, включая миграцию с 0.1, и собирает Docker.
Тесты транспорта проверяют модели закреплённого PyMax, а не доступ к живому MAX.

## Обновление и резервные копии

```bash
bash scripts/backup.sh
git pull --ff-only
docker compose up -d --build
docker compose ps
```

Отдельно сохраните `.env` и ключи шифрования. Не используйте `docker compose down -v`
для обновления: это удаляет данные. Миграции последовательные, без downgrade;
откат версии требует согласованной копии БД. Имя сервиса приложения — `bot`.

Ключи `ENCRYPTION_KEYS` перечисляются через запятую: первый шифрует новые записи,
старые нужны для чтения существующих. Не удаляйте старый ключ без пере-шифрования
и проверки восстановления всех сессий/очередей. `.env` не должен попадать в Git.

## Диагностика

`/status` показывает состояние и очередь; `/help` — команды.
`/retry N confirm` допускает повтор после неопределённого результата только с
осознанным риском дубля. `/skip N` освобождает последующие сообщения диалога.
Не редактируйте ID получателей в БД вручную. Когда создание темы завершилось
неопределённо, найдите её и отправьте `/bind UUID` внутри темы, как подсказывает бот.

При потере сообщения-подтверждения уведомление об отзыве сессии может повториться;
это предпочтительнее молчаливого отключения. Логи не содержат текстов сообщений,
паролей или сырых MAX-ошибок. Не включайте отладочные payload-логи PyMax в production.
Один процесс удерживает advisory lock; второй экземпляр не запускается.
