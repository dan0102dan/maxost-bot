# MAXOST · MAX ↔ Telegram

Первая версия многопользовательского моста. Пользователь открывает Telegram-бота,
подключает **свой личный аккаунт MAX** и получает отдельную тему для каждого
собеседника. Ответ в теме отправляется в соответствующий диалог MAX от его имени.

**Статус: v0.1 / alpha.** Реализация написана под проверенную документацию
Telegram Bot API и конкретный commit PyMax. Нужна проверка с настоящими аккаунтами
перед публичным запуском. Ни библиотека, ни проект не являются официальным
клиентом MAX. Использование внутреннего API может привести к поломке интеграции
или ограничениям аккаунта.

## Что реализовано

- Несколько независимых пользователей Telegram; один MAX-аккаунт на пользователя.
- SMS-авторизация через **настоящий RichMessage**: экран номера, клавиатура 3×4,
  удаление цифры, очистка, подтверждение, маскированный код, отмена, тайм-аут.
- Поддержка дополнительного пароля MAX (2FA). Он вводится отдельным сообщением;
  бот пытается удалить его сразу. Это не защищённый канал ввода паролей: Telegram
  всё равно получает текст. Телефон и SMS вводятся кнопками, а не сообщениями.
- Автоматическое создание личных тем и постоянная привязка по ID, не по имени.
- Текст, фото, документы, видео, голосовые. Вложения до 20 МБ в обе стороны;
  размер можно уменьшить настройкой. Подпись передаётся отдельным текстом.
- Ответы на сообщения, текстовые редактирования при неизменном числе частей,
  удаления MAX → Telegram и явная команда `/delete` Telegram → MAX.
- PostgreSQL: ограничения уникальности, составные внешние ключи владельца,
  миграции, зашифрованные сессии и очередь, дедупликация, восстановление очереди.
- Повтор безопасных запросов, ручной разбор неопределённых результатов,
  блокирование последующих заданий того же диалога/направления до разбора ошибки.
- Переподключение MAX и ограниченная постраничная проверка истории после точки
  подключения; полная начальная история не выгружается.
- Отзыв подключения, удаление данных пользователя, очистка содержимого после
  доставки, срок хранения метаданных, ограничение попыток входа и вместимости.
- Docker Compose, PostgreSQL healthcheck, непривилегированный контейнер,
  read-only filesystem, CI с PostgreSQL и сборкой образа.

## Быстрый запуск

### 1. Подготовьте Telegram-бота

Создайте бота через **@BotFather** и включите **forum topic mode в личных чатах**.
`getMe.has_topics_enabled` должен быть `true`; иначе приложение завершится при
проверке конфигурации. Для управляемых тем желательно запретить пользователям
их создание/удаление, но для ручного восстановления `/bind` тема должна уже
существовать. Никакая Telegram-группа не нужна.

Используется long polling. У этого токена не должно быть действующего webhook
или другого процесса `getUpdates`. Приложение не удаляет чужой webhook молча.
Для RichMessage нужен поддерживающий его Bot API/клиент Telegram. `RICH_UI=false`
включает явный запасной вариант HTML + inline-клавиатура.

### 2. Создайте конфигурацию

```bash
git clone https://github.com/dan0102dan/maxost-bot.git
cd maxost-bot
python3 scripts/configure.py
```

Скрипт запросит токен без отображения ввода, сгенерирует пароль PostgreSQL и
32-байтовый ключ шифрования, создаст `.env` с правами `0600`. Существующий `.env`
он **не перезаписывает**. Для первой проверки задайте `ALLOWED_TELEGRAM_IDS`
двумя своими тестовыми пользователями; пустое значение открывает регистрацию всем.

Требуются Docker Engine и Docker Compose plugin. После настройки:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 -f bot
```

Затем откройте бота, отправьте `/start`, прочитайте условия доступа, введите номер
с кодом страны на клавиатуре, запросите SMS и подтвердите код. Попросите собеседника
отправить сообщение в MAX. Его тема появится автоматически; ответьте внутри неё.

На хосте не нужны Python-зависимости проекта; `configure.py` использует только
стандартную библиотеку. В сборочном контейнере установлен Git для неизменяемой
зависимости PyMax; в рабочем контейнере его нет. Внешние порты не публикуются.

## Конфигурация

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `TELEGRAM_BOT_TOKEN` | обязательно | Токен Telegram-бота |
| `ENCRYPTION_KEYS` | обязательно | Base64-ключи AES-256-GCM, активный первым |
| `POSTGRES_PASSWORD` | обязательно для Compose | URL-safe пароль PostgreSQL |
| `DATABASE_URL` | формируется Compose | DSN PostgreSQL для приложения |
| `ALLOWED_TELEGRAM_IDS` | пусто | Ограничение регистрации и доступа по ID |
| `MAX_ACCOUNTS` | 100 | Лимит подключений, **не обещание производительности** |
| `WORKERS` | 4 | Параллельные обработчики очереди |
| `AUTH_TTL_SECONDS` | 600 | Время существования экрана авторизации |
| `MAX_FILE_MB` | 20 | Предельный размер вложения, максимум 20 |
| `HISTORY_MAX_PAGES` | 20 | Предел страниц чатов/истории за проверку |
| `HISTORY_INTERVAL_SECONDS` | 120 | Интервал проверки пропущенных сообщений |
| `RETENTION_DAYS` | 30 | Срок метаданных, дедупликации и недоставленного содержимого |
| `RICH_UI` | true | RichMessage вместо запасной inline-клавиатуры |

Приложение также принимает `TELEGRAM_BOT_TOKEN_FILE`, `ENCRYPTION_KEYS_FILE` и
`DATABASE_URL_FILE` для внешнего secret manager/Docker secrets. При самостоятельной
настройке DSN экранируйте специальные символы пароля. Сгенерированный пароль
URL-safe. `docker compose config` и `docker inspect` могут показывать переменные:
не публикуйте их вывод.

## Команды

`/connect`, `/status`, `/help`, `/cancel`, `/disconnect`.

`/delete` — ответом на **своё** сообщение, отправленное через мост.
Обычное удаление в Telegram не синхронизируется: Bot API не присылает универсальные
события удаления обычных личных сообщений.

`/retry 123` — безопасный ручной повтор известной ошибки.
`/retry 123 confirm` — повтор с риском дублирования после неизвестного результата.
`/skip 123` — удалить содержимое задания и разблокировать следующую доставку.

`/bind UUID` — внутри существующей темы восстановить потерянную привязку.
UUID показывается в сообщении ошибки, короткая часть — в названии созданной темы.
Команда не перепривязывает уже используемую тему и не отправляет задания сама.
После неё используйте `/retry N` (или подтверждённый повтор, если требуется).

## Устройство проекта

```text
maxost/
  main.py             long polling, команды, lifecycle, singleton guard
  auth.py, ui.py      авторизация, ephemeral state, RichMessage
  max_client.py      адаптер PyMax и независимые соединения
  session_store.py   StoreProtocol → зашифрованный PostgreSQL
  telegram.py        прямой HTTP Bot API, классификация ошибок
  bridge.py          маршрутизация, доставка, темы, восстановление
  media.py           вложения, ограничения и SSRF-защита загрузок
  db.py, migrations/ транзакции, очередь, уникальность и ownership
  crypto.py          версионированные AES-GCM envelopes
  content.py         нормализация текста, имён и вложений
```

На первой версии работает **один процесс приложения** с несколькими MAX-клиентами
и воркерами. PostgreSQL advisory lock не позволяет штатно запустить второй poller.
Это не HA-кластер: масштабирование аккаунтных соединений и безопасные распределённые
leases ещё потребуют отдельного проектирования. Для одного пользователя всегда
проверяются пары `account_id + owner`, `dialog_id + owner`, `chat_id + thread_id`.

Очередь одновременно служит журналом принятых событий. Сначала событие сохраняется,
затем подтверждается Telegram offset. Повтор обновления упирается в `UNIQUE`.
Воркеры захватывают задания через `FOR UPDATE SKIP LOCKED`; в одном направлении
диалога следующее задание не обгоняет нерешённое предыдущее.

До внешнего побочного эффекта сохраняется `sending`. После успеха сопоставление ID
и `sent` фиксируются одной транзакцией. При падении между отправкой и подтверждением
задание становится `unknown`, а не отправляется повторно вслепую. **Exactly-once
между двумя внешними мессенджерами не гарантируется.** Ошибки/unknown блокируют
только соответствующее направление диалога и отображаются владельцу.

## Ограничения первой версии

- Только личные диалоги MAX; не группы/каналы и не MAX Bot API.
- Сообщения, написанные владельцем непосредственно в приложении MAX, не
  зеркалируются. Все собственные MAX-события подавляются для защиты от эха.
- Нет звонков, реакций, typing/read receipts, стикеров, опросов, альбомов как
  единого объекта, полного переноса форматирования. Неизвестное входящее вложение
  обозначается текстом, а не молча теряется.
- В PyMax исходящий текст проходит Markdown-подобный обработчик. Обычный текст
  переносится; полное соответствие entity offsets/литеральных маркеров не обещается.
- Изменение вложения или количества текстовых частей при редактировании требует
  нового сообщения. Видео-кружки из Telegram отправляются как VideoNote; видео
  из MAX, в том числе некоторые кружки, отображается обычным видео.
- Исходные медиа скачиваются при доставке по обновлённой ссылке. Если они уже
  удалены, недоступны или слишком велики, задание получает явную ошибку.
- Начальная история до подключения не переносится. Проверка пропущенной истории
  ограничена страницами. При достижении лимита/непродвижении курсора контрольная
  точка не сдвигается; это видно по `/status` и обезличенному предупреждению в логе.
  Восстановление всех событий редактирования/удаления во время офлайна не обещается.
  Смешение live-событий с историей может влиять на хронологию после обрыва.
- Telegram хранит необработанные Bot API updates не более 24 часов. Длительный
  простой Telegram-части не может быть полностью компенсирован этой программой.
- Срок дедупликации ограничен `RETENTION_DAYS`. Долгие простои/восстановление старой
  резервной копии требуют проверки на повторы.
- При отзыве токена MAX нужно отключить старое подключение и пройти вход заново.
  Никакого автоматического повторного запроса SMS после рестарта нет.

## Безопасность и данные

Сессии MAX, номера телефонов, названия собеседников и содержимое очереди зашифрованы
AES-256-GCM. В AAD включён владелец и назначение записи; перенос ciphertext между
пользователями не пройдёт проверку. ID и технические статусы остаются в открытом виде.
SMS/2FA не сохраняются; процесс держит их в памяти на время проверки. После успешной
доставки содержимое задания удаляется; ID сохраняются до окончания retention.

Это **не сквозное шифрование и не защита от оператора сервера**: серверу нужен ключ,
чтобы подключаться и пересылать. Владелец сервера, процесс с его правами и компрометация
runtime могут получить доступ к аккаунтам. Перед публичным доступом разместите свою
политику обработки переписки, контакт оператора и используйте доверенную инфраструктуру.

В логах приложения нет текстов сообщений, токенов, номеров и полных исключений.
Не включайте DEBUG для библиотек. Загрузчик MAX-вложений разрешает только HTTPS
на публичные IP, проверяет DNS-адреса непосредственно в resolver соединения,
ограничивает размер и повторно проверяет перенаправления. Код не выполняет файлы.

`/disconnect` останавливает отправку, пытается отозвать MAX-сессию и удаляет активные
данные сервиса. Если MAX недоступен, пользователь получает указание завершить сессию
в настройках устройств MAX. Сообщения уже в мессенджерах и старые резервные копии
автоматически не удаляются. Антиабузные записи попыток входа сохраняются до суток.

## Резервная копия и обновление

```bash
sh scripts/backup.sh
# Отдельно и безопасно сохраните .env / ENCRYPTION_KEYS.
git pull --ff-only
docker compose up -d --build
```

Не выполняйте `docker compose down -v`, если хотите сохранить БД. Удаление ключей
делает зашифрованные сессии нечитаемыми. Резервная копия БД без ключей не восстановит
доступ; резервная копия вместе с ключами столь же чувствительна, как сами аккаунты.

Восстановление в пустую/подготовленную БД (бот должен быть остановлен):

```bash
docker compose stop bot
docker compose exec -T postgres pg_restore -U maxost -d maxost --clean --if-exists < backups/your-backup.dump
docker compose up -d bot
```

Поддержан key ring: `ENCRYPTION_KEYS=новый,старый`. Новые записи шифруются первым
ключом, старые читаются соответствующим ключом по ID. **Не удаляйте старый ключ:**
массовая перешифровка и смена HMAC-индекса телефона ещё не автоматизированы; последний
ключ также используется для стабильных HMAC-индексов.

## Проверки

```bash
python -m venv .venv
. .venv/bin/activate
pip install . -r requirements-dev.txt
pytest -q
ruff check maxost tests
```

Без `TEST_DATABASE_URL` настоящие PostgreSQL-тесты пропускаются. Без установленного
PyMax пропускаются signature contract tests. CI устанавливает зависимости, поднимает
одноразовый PostgreSQL, запускает обе группы и собирает Docker-образ. CI **не**
авторизуется в MAX и не отправляет личные сообщения.

В среде подготовки: **40 тестов прошли, 6 пропущены** (PostgreSQL/PyMax отсутствуют).
Docker Engine и реальные токены в этой среде отсутствовали. Результат CI после
загрузки нужно смотреть отдельно, не считать тестирование настоящих API выполненным.

### Обязательная первая проверка с двумя пользователями

1. Ограничьте `ALLOWED_TELEGRAM_IDS` двумя тестовыми Telegram-аккаунтами.
2. Оба входят в разные собственные MAX-аккаунты через кнопки. Проверьте неверный код,
   отмену, истечение экрана, повторное нажатие старой клавиатуры и 2FA.
3. Один и тот же собеседник MAX пишет обоим: темы должны быть независимыми. Ответы
   каждого пользователя должны уйти с правильного MAX-аккаунта правильному человеку.
4. Проверьте фото/файл/голосовое, ответ, правку текста и явное удаление.
5. Перезапустите `bot`, убедитесь, что SMS не требуется, привязки сохранены, новые
   сообщения доставляются. Проверьте доступность истории после отключения сети.
6. Проверьте `/disconnect`: очередь остановлена, данные удалены, удалённая сессия
   отозвана либо показано предупреждение о необходимости ручного отзыва.
7. Только после проверки снимайте allowlist и увеличивайте лимиты по результатам
   наблюдения CPU, памяти, количества соединений и очереди.
